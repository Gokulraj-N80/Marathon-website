BUG-001 — Race ID Mismatch Between Frontend and Backend
--------------------------------------------------------
Severity   : P0 / Critical
Files      : marathon frontend/src/data/marathon.ts
             backend/server.js
             backend/seed-test.js

Description:
  The frontend defines the Half Marathon race ID as "half":
    data/marathon.ts: RACES[0].id = "half"

  The backend fee-map, BIB generator, and seed data all use "21k":
    server.js:52     feeMap = { "5k": ..., "10k": ..., "21k": ... }
    server.js:1228   racePrefix = raceId.toUpperCase() -> "HALF"
    seed-test.js:31  races = ["5k", "10k", "21k"]

Impact:
  - Every Half-Marathon registration sends raceId="half"
  - Backend fee lookup falls through to default -> Rs 799
  - BIB becomes e.g. CHE-HALF-0001 instead of CHE-21K-0001
  - Stats/reports group half-marathon under wrong key

Evidence (frontend):
  data/marathon.ts line 58:
    { id: "half", distance: "21.1", type: "Half Marathon", ... }

Evidence (backend):
  server.js line 50-52:
    const raceLabel = participant.raceId === "5k" ? ...
    const feeMap = { "5k": "499", "10k": "799", "21k": "999" };
    const fee = feeMap[participant.raceId] || 799;

Recommendation:
  Change frontend id from "half" to "21k" so it matches backend.

BUG-002 — Registration Fees Do Not Match Across Frontend, Backend, README
--------------------------------------------------------------------------
Severity   : P0 / Critical
Files      : marathon frontend/src/data/marathon.ts
             backend/server.js (fee-map, emails)
             README.md

Description:
  Frontend charges one price; backend processes and emails charge a
  different price. README matches neither consistently.

  Category   | Frontend | Backend (feeMap) | README
  -----------|----------|------------------|--------
  5K Fun Run | Rs 349   | Rs 499           | Rs 499
  10K Run    | Rs 499   | Rs 799           | Rs 799
  Half       | Rs 699   | Rs 999           | Rs 999

Impact:
  - Runner pays frontend price but backend calculates + emails show
    a different amount
  - Revenue reports are wrong
  - Support queries and disputes guaranteed at scale

Evidence:
  data/marathon.ts line 58-60:
    { id: "half", fee: "699" }
    { id: "10k",  fee: "499" }
    { id: "5k",   fee: "349" }

  server.js line 52:
    const feeMap = { "5k": "499", "10k": "799", "21k": "999" };

  README line 71-73:
    5K Rs 499, 10K Rs 799, Half Rs 999

Recommendation:
  Choose one fee set and apply it everywhere. Best practice:
  store fees in a shared config or env, not as duplicated literals.

BUG-003 — No Server-Side Validation on /api/register
-----------------------------------------------------
Severity   : P0 / Critical
Files      : backend/server.js

Description:
  POST /api/register creates a Mongoose document directly from req.body
  with NO schema validation at the API layer.

  server.js line 1144:
    const newParticipant = new Participant(req.body);
    await newParticipant.save();

Impact:
  - Frontend Zod validation can be bypassed with curl / Postman
  - Missing required fields -> 500 error instead of clean 400
  - Mongoose schema is weak: no unique index on email/phone
  - No input sanitization -> potential NoSQL injection risk
  - Duplicate email registrations are accepted

Evidence:
  server.js schema (line 1078):
    fullName: { type: String, required: true },  <- required
    phone:    { type: String, required: true },  <- required
    email:    { type: String, required: true },  <- required
    // No unique: true anywhere
    // No enum validation for gender/cityId/raceId/size

Recommendations:
  1. Add a Zod schema on the backend mirroring the frontend one
  2. Reject with 400 before hitting the database
  3. Add unique indexes on email and phone
  4. Add rate limiting on public endpoints
  5. Add input sanitization / escape MongoDB operators

BUG-007 — BIB Number Can Be Lost on Payment Toggle
---------------------------------------------------
Severity   : P1 / High
Files      : backend/server.js

Description:
  When an admin toggles payment from Paid -> Pending, the BIB is
  cleared. If toggled back to Paid, a NEW BIB is generated,
  destroying the original one.

  server.js line 1232-1234:
    } else if (paymentStatus === "Pending") {
      participant.bibNumber = "";
    }

  line 1221-1222:
    if (paymentStatus === "Paid" && !participant.bibNumber) {
      // generates a new bib

Impact:
  - Participant certificates, emails, and check-in records all
    reference the original BIB; admin action invalidates that data
  - Revenue and attendance tracking become unreliable

Recommendation:
  - Do NOT clear bibNumber on Pending
  - Either persist original BIB or maintain a BIB history collection

BUG-020 — Double-Slash Risk in API_BASE Construction
-----------------------------------------------------
Severity   : P3 / Low
Files      : marathon frontend/src/components/admin/types.ts

Description:
  types.ts line 51:
    export const API_BASE = `${import.meta.env.VITE_API_URL || "http://localhost:5000"}/api/admin`;

  If VITE_API_URL = "http://localhost:5000/" (trailing slash),
  URL becomes http://localhost:5000//api/admin (double slash).

Impact:
  - Most HTTP clients normalize double slashes, but some proxies/CDNs
    may reject or redirect unexpectedly

Recommendation:
  Strip trailing slash before appending path.
